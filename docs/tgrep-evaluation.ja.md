# tgrep v1.0.5 のローカル比較

2026-09-09、kiokuko-ai `701f136b07e581349688971324f83ca6adb5b625` の現行ソースで実行。
検索候補を絞る用途には有望。ただし、この規模での短縮は通常1検索あたり数msであり、Enno全体の速度・入力tokens・計画品質の改善は証明していない。今回は評価スクリプトと測定記録を追加し、製品の検索経路やEnnoの自動実行は変更していない。

## 条件

- macOS arm64、tgrep 1.0.5、ripgrep 15.1.0。
- Git管理下の `src/`・`tests/` とrootのignoreファイル、計441ファイル・6,767,566 bytesを一度だけ一時コピー。元リポジトリのファイルは編集しない。コピー先に編集試験用ファイルを1つ追加。
- 元の未追跡ripwire評価ファイル・node_modulesは含めない。コピー内でGitを初期化してtracked/ignore判定を有効にする。
- corpus SHA-256: `1b54543b08b8a6b0fc8abeec0a1d97fa3a7ea8b6c46b2c5c05c387e251d5efee`。
- 12種類の検索を各10回。モデル経路、MCP期限、advisory、repository-state、lease、管理ファイル更新、キャンセル、dispatch digest、大小文字無視、日本語の実在語、短い語、不在語。自然言語による課題解決の比較ではない。
- 本文検索はJSON・前後2行、ファイル上限2 MiBを揃える。ファイル名のみの検索は `-l --null`。方式の実行順を交代する。
- 新しい索引を作成し、初回の状態照合とnative watcher起動を確認してから検索。OSのファイルキャッシュは温まっているため、OSキャッシュまで空にしたcold測定ではない。
- CLI時間はプロセス起動と出力受信を含む。RPCは同じ接続を維持し、JSON解析まで含む。RPC側はすでにCLI経由で検索された索引・検索キャッシュを使用する。

## 結果

各検索の10回の中央値を求め、その12件の中央値を掲載。

| 方式 | 本文・前後2行 | ファイル名のみ |
|---|---:|---:|
| rg 通常 | 10.86 ms | 9.92 ms |
| rg 単一スレッド | 12.71 ms | 11.27 ms |
| tgrep CLI＋常駐サーバー | 6.45 ms | 5.63 ms |
| tgrep 常駐サーバーへ直接RPC | 0.80 ms | 未測定 |

本文ではCLIで約41%、直接RPCで約93%短縮。ただし、これをLLM処理全体の短縮率として使ってはいけない。

12件の検索時間の中央値を**合計**すると、本文検索はrg 132.80 ms、tgrep CLI 124.66 ms、RPC 39.18 ms。CLIの合計差は約8 msに留まる。短い語 `db` は7,643行の一致・文脈を返し、rg 14.12 msに対しtgrep CLI 46.66 ms、RPC 27.05 msと逆転した。中央値だけで万能な高速化と判断できない。

ファイル名だけなら12件合計はrg 120.42 ms、tgrep CLI 69.10 ms。まず対象ファイルを絞る使い方の方が安定している。

初期索引作成78.55 ms、サーバー起動・初回状態照合25.78 ms、計104.33 ms。評価用コピーの準備440.29 msは別途必要だった。索引は約5.55 MiB、常駐プロセスのRSSは1回の観測で約46.4 MiB。初期費用は検索のwarm時間に含まれておらず、一度だけの検索が速いという結果ではない。

全検索・全反復で、rgとtgrep CLI/RPCの相対パス・行番号・match/context種別・本文が一致。ファイル名のみの集合も一致した。日本語 `二重実行` は実際に一致行と前後の文脈を取得した。バイナリ、非UTF-8、全オプション、submatch offsetの互換性までは検証していない。

同じ投影後の検索本文・ファイル一覧は同一であり、この試験ではtgrep固有の情報量削減はない。`-l`で取得量を減らせるのはrgも同じ。実LLMの入力tokens、追加探索・実装確認時間、計画品質は未測定。モデル呼び出しや外部へのソース送信は行っていない。

## 編集の反映

| 操作 | 直後の索引検索 | 再確認した結果 |
|---|---|---|
| 同じサイズで本文編集 | 不一致 | 約56 ms時点で一致 |
| 未追跡ファイル追加 | 不一致 | 約53 ms時点で一致 |
| rename | 不一致 | 約52 ms時点で一致 |
| 削除 | 不一致 | 約51 ms時点で一致 |
| ignore対象への追加 | 除外 | 500 ms後の再検査でも除外 |
| 外部ファイルへのsymlink追加 | 除外 | 500 ms後の再検査でも除外 |

時間にはrgによる照合、tgrepの全走査による照合、20 msの再照会間隔が含まれる。これはwatcherの厳密な遅延測定や「56 ms待てば必ず最新」という保証ではない。除外試験も任意のツリーに対する安全性の証明ではない。

サーバーを終了してからファイルを変更すると、ディスク索引の検索では追加した語を発見できなかった。同じ条件の `tgrep --no-index` はrgと一致した。すべての編集試験で `--no-index` はその時点のrgと一致した。

## kiokuko-aiでの位置づけ

現段階では、通常の読み取り調査でファイル候補を絞る任意の検索手段とする。Ennoの事前チェックに独立した必須工程を増やす根拠はない。

組み込むなら、親が保持する一つの検索サーバーをidealとZenkiで共有し、最初はファイル名を取得、必要な場所だけ本文を読む。参照する実装は実ファイルで確認する。編集直後・サーバー再起動時・一致なしを根拠にする調査では、rgまたは `--no-index` で確認する。サーバー不在時にディスク索引を透過的に採用すると、古い索引による取りこぼしを隠すので避ける。

直接RPCなら今回の検索自体は速いが、サーバーの所有・停止・予算・出力検証・鮮度の扱いが追加責務になる。この管理費用を含む製品経路は未実装・未測定。数msの短縮を理由にripwire統合と同規模の仕組みを先に作るべきではない。

## 再実行

[評価スクリプト](../scripts/evaluate-tgrep.mjs) はNode標準ライブラリのみを使う。明示したバイナリを検査し、一時コピー・索引・127.0.0.1の所有サーバーを作り、終了時に回収する。ダウンロードやglobal installはしない。通常のmacOS環境でリポジトリrootから実行する。サンドボックス内ではloopbackサーバー起動の許可が必要になる場合がある。

```sh
node scripts/evaluate-tgrep.mjs \
  /tmp/kiokuko-tgrep-v1.0.5-bin/tgrep \
  docs/tgrep-evaluation.json
```

今回検証して配置したバイナリは上記の一時パスにある。一時ファイルが消えた場合は、[公式v1.0.5リリース](https://github.com/microsoft/tgrep/releases/tag/v1.0.5)から対象バイナリを取得して絶対パスを指定する。

- 使用アセット: `tgrep-v1.0.5-aarch64-apple-darwin.tar.gz`
- アーカイブSHA-256: `aa7644819d3a6e0202013e6c7c2be2623d5a2bef710249c0b31cc00aa80e19ad`
- ダウンロード後にGitHub公開digestと照合し、アーカイブの内容を確認してバイナリだけを取り出した。
- [固定版の上流README](https://github.com/microsoft/tgrep/blob/v1.0.5/README.md)、[サーバー実装](https://github.com/microsoft/tgrep/blob/v1.0.5/tgrep-cli/src/serve.rs)。loopback bindと検索・状態取得のJSON-RPC実装を確認した。

詳細な各回の時間・出力bytes・一致digest・状態情報は [測定JSON](./tgrep-evaluation.json) に記録。通常のアプリケーションテストは今回変更していない製品経路を検証するため未実施。スクリプトの構文確認と実バイナリでの比較実行が今回の検証範囲。
